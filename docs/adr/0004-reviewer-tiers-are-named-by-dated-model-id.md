# Reviewer tiers are named by dated model id, not family alias

`adversarial-review` named its two tiers with harness family aliases — `sonnet` for seeds, `opus` for resolvers — and said so normatively: "a harness alias, never a dated model id." As of `dev-flow` 2.11.0 and `dev-flow-worktree` 1.13.0 the tiers are `claude-sonnet-4-6` and `claude-opus-4-8`. `CONTEXT.md`'s **Tier** entry follows, and the self-report check is renamed from **family match** to **tier match**, since matching a family is now its fallback rather than its definition.

The reason is the failure mode aliases have: an alias resolves to whatever the newest model in its family is, so every release silently re-points both tiers. Opus 5 and Sonnet 5 shipped and the reviewers got worse for us with no change to this repo and nothing in the protocol to point at. A tier whose model can change without an edit here is not a tier this repo chose; it is one the release calendar chooses. Pinning moves that choice back into the file, where the version-bump discipline already makes it deliberate.

Two honest limitations. First, the Agent tool's `model` parameter currently accepts only family aliases (`sonnet`, `opus`, `haiku`, `fable`), so a spawn requested as `claude-opus-4-8` still lands on the newest Opus today. The dated id is what the protocol *requests*; tier match accepts a same-family model so an alias-only interface does not halt every run, and provenance records the model that actually ran — so the gap is visible in each review's report rather than silent. When the spawn interface takes a dated id, the pin binds with no further edit. Second, the Sonnet line has no 4.8: 4.6 is the newest Sonnet before 5, so the seed tier is 4.6 by availability, not by preference.

The cost accepted is maintenance. A pinned id is deprecated and eventually retired, and someone must bump it; that recurring edit is exactly what the alias was buying. It is the right trade here because the alias bought it by giving away reproducibility, and a review protocol whose judgment tier moves underneath it cannot be tuned against.

This revises ADR 0002 only where it argues for aliases. Its substantive decision — resolvers unconditionally in the Opus family, `adversary ≠ author` abandoned, provenance claiming only fan-out — stands unchanged.

## Considered options

- **Keep the aliases and pin the session model to `claude-opus-4-8` instead** — rejected: it moves executors, fixers, and the orchestrator, which run on the main session model, but seeds and resolvers are pinned by tier rather than inherited from the session, so the two tiers that actually regressed would stay on their family's newest model. It also puts the reviewer tier back under ambient state, which is what ADR 0002 rejected.
- **Ship agent-definition files carrying the dated id in frontmatter, spawned by `subagent_type`** — deferred, not rejected. This is the only route that makes the pin bind under today's spawn interface, since frontmatter `model:` accepts a full id. It is a larger restructure: the reviewer prompts move out of `SKILL.md` into per-plugin agent files in both variants, and because the Agent tool's `model` parameter overrides frontmatter, the skills would additionally have to guarantee they never pass one. Worth doing when the reviewer prompts are next reworked; not worth coupling to a tier change.
- **Halt when the dated id cannot be honored**, treating an alias-only interface as "a required model unavailable" — rejected: that is literally every run today, so it trades a visible model substitution for a total outage of both pipelines.
- **Name the tier by family plus a floor** (e.g. "Opus, at most 4.8") — rejected: no spawn interface expresses it, so it would be a constraint no caller can act on and no check can verify beyond what tier match already does.
